# Week 07 in class — From reset to page tables: boot, the free list, and Sv39

Companion material for the [Week 7 lecture](https://cs326-f26.cs.usfca.edu/lectures/07-cs326-2026-10-06-boot-physical-pages-and-sv39/) (October 6, 2026). The
lecture page makes the arguments; this material is the part you *run*. Three
exercises come due this week: `31k_boot` and `32k_physical_memory` on
Thursday, then `33k_paging` on Friday. The programs are grouped the same way.

Like week 6, every program is a bare-metal RISC-V binary that QEMU starts
with no firmware and no OS. This week they look at the machine that runs
them: the boot ROM that ran before them, where the linker put each of their
bytes, the stack they run on, the free RAM above it, and the bits of the page
tables rv6 is about to build.

## Running it

```bash
cd examples
cargo run --bin 01_the_boot_rom      # ... through 13_w_xor_x
```

`cargo run` builds for `riscv64gc-unknown-none-elf` and hands the ELF to
`qemu-system-riscv64`, the same line `oslings run` uses. Each program prints
over the UART and powers QEMU off when it is done; if one ever hangs,
<kbd>Ctrl</kbd>-<kbd>A</kbd> then <kbd>x</kbd> quits QEMU.

```bash
cd examples && ./show-errors.sh
```

`show-errors.sh` walks all nine compile failures for the same bare-metal
target, pausing between each; pass a substring to jump to one:
`./show-errors.sh e0606`. Nothing under `broken/` is part of the package.

`examples.html` is captured output only, as in week 6: a browser cannot boot
a RISC-V board, so there is no **Edit and run**. Rebuild it from the repo root
with `python3 tools/pointat.py week07`, which needs QEMU.

## The runtime

`src/lib.rs` is week 6's runtime with two additions. `week07::Hex` prints a
number the way the lecture writes addresses, `0x8123_4000`; `{:.8}` asks for
at least eight digits. And the start function turns the FPU on before `main`:
QEMU resets with `mstatus.FS = 0`, so without it the first floating-point
instruction, such as formatting an `f64`, traps to `mtvec = 0` and the
machine hangs without a word. (Week 6's runtime now does the same.)

The stack sits directly above the image, from `end` to `__stack_top`. That
is one difference from rv6, whose boot stack is an array inside `.bss`, below
`end`. So rv6's free memory starts at `end`, and this runtime's starts at
`__stack_top`; programs 02 and 08 say so where it matters.

## Step by step, on screen

The same walk as week 6's README, pointed at this week's programs: build the
ELF, look inside it, then stop the machine at reset and read the boot ROM,
the registers and RAM with QEMU's monitor, and check the page arithmetic by
hand. Everything runs from `week07/examples`. The addresses in the output
shown are from one build and move when the code does.

Rust's own LLVM tools read the ELF (`rustup component add llvm-tools` if
the directory is empty):

```sh
cd week07/examples
BIN="$(rustc --print sysroot)/lib/rustlib/$(rustc -vV | sed -n 's/^host: //p')/bin"
E=target/riscv64gc-unknown-none-elf/debug
```

**0. The one-liner.**

```sh
cargo run --bin 01_the_boot_rom
```

Cargo's `Running` line is the QEMU command: `cargo run` is a build, then that.

**1. Build, and see that the Mac cannot run the result.**

```sh
cat .cargo/config.toml                    # the target, -Tlink.ld, and QEMU as the runner
touch src/bin/01_the_boot_rom.rs
cargo build -v --bin 01_the_boot_rom      # point at --target, --extern week07=…, -Clink-arg=-Tlink.ld
file $E/01_the_boot_rom                   # ELF 64-bit LSB executable, UCB RISC-V, ... statically linked
./$E/01_the_boot_rom                      # exec format error
```

**2. The layout program 02 prints, read straight from the ELF.**

```sh
cargo build -q --bin 02_where_the_linker_put_it
"$BIN/llvm-objdump" -h $E/02_where_the_linker_put_it
"$BIN/llvm-nm" -n -C $E/02_where_the_linker_put_it | grep -E ' (_entry|etext|end|__stack_top)$|COUNT|TABLE'
```

```
0000000080000000 T _entry
0000000080002000 T etext
0000000080002ce0 d _02_where_the_linker_put_it::COUNT::h…     d: .data
0000000080002cf0 b _02_where_the_linker_put_it::TABLE::h…     b: .bss
0000000080003cf0 B end
0000000080007cf0 B __stack_top
```

These are the addresses program 02 prints, because it is the same file.
`.text` is `0x2000` bytes, two pages, and `etext` is where it ends.

**3. `_entry`, and code the program will rewrite.**

```sh
"$BIN/llvm-objdump" -d --no-show-raw-insn --start-address=0x80000000 --stop-address=0x8000000c $E/01_the_boot_rom
cargo build -q --bin 13_w_xor_x
"$BIN/llvm-objdump" -d -C --no-show-raw-insn $E/13_w_xor_x | grep -A2 '<answer>:'
```

`_entry` is `auipc sp` and `addi sp` (together `la sp, __stack_top`), then
`j __week07_start`. In the file, `answer` is `li a0, 0x7` then `ret`, yet
program 13 prints `answer() = 42`: it stores a new instruction over that one
while it runs. With paging off, nothing stops it.

**4. Run QEMU by hand.**

```sh
qemu-system-riscv64 -machine virt -bios none -m 128M -smp 1 -nographic -serial mon:stdio -kernel $E/01_the_boot_rom
echo $?        # 0: the runtime powered off through the test finisher
```

`-machine virt` is the board, `-bios none` means no firmware, `-m 128M` puts
the end of RAM at `0x8800_0000`, `-smp 1` is one hart,
`-nographic -serial mon:stdio` makes the UART your terminal with the monitor
behind <kbd>Ctrl</kbd>-<kbd>A</kbd> <kbd>c</kbd>, and `-kernel` loads the ELF.
Week 6's README has the table.

**5. Watch reset happen.**

```sh
qemu-system-riscv64 -machine virt -bios none -m 128M -smp 1 -nographic -serial mon:stdio \
  -d in_asm -D qemu.log -kernel $E/04_reset_to_rust
grep '^0x' qemu.log | head -14
```

In order: the ROM's six instructions at `0x1000`, which program 01
decodes; `_entry`'s `auipc sp`, `addi sp` and `j`; then `__week07_start`'s
prologue, `addi sp,sp,-16` and `sd ra,8(sp)`, and `lui t0,2` with
`csrrs zero,mstatus,t0`, the FPU turned on. `qemu.log` is git-ignored.

**6. Stop at reset and read the machine.** `-S` holds the CPU before its first
instruction:

```sh
qemu-system-riscv64 -machine virt -bios none -m 128M -smp 1 -nographic -serial mon:stdio -S -kernel $E/01_the_boot_rom
```

Press <kbd>Ctrl</kbd>-<kbd>A</kbd> then <kbd>c</kbd>, and at `(qemu)`:

| Type | QEMU shows | Program |
|---|---|---|
| `x /6i 0x1000` | the boot ROM, disassembled: `auipc t0,0` … `jr t0` | `01`, second section |
| `xp /2xg 0x1018` | `0x0000000080000000 0x0000000087e00000`: the jump target, then the device tree | `01`, third section |
| `info registers` | `pc 0000000000001000`, `sp` 0, `satp 0000000000000000` | `04`, `12` |
| `info mem` | `No translation or protection`: paging is off | `12` |
| `xp /4xg 0x87fff000` | zeros: the top page of RAM, untouched | `07`, `08` |

`cont` runs the program to the end; `q` quits instead, and
<kbd>Ctrl</kbd>-<kbd>A</kbd> then <kbd>x</kbd> works at any point.

**7. The page arithmetic, in the shell.** zsh and bash both do 64-bit hex:

```sh
printf '0x%x\n' $(( (0x80007cf0 + 0xfff) & ~0xfff ))       # round up to a page: 0x80008000 (program 08)
printf '%d\n'   $(( (0x88000000 - 0x80008000) >> 12 ))     # whole pages to the end of RAM: 32760
printf '0x%x\n' $(( ((0x81234000 >> 12) << 10) | 7 ))      # the lecture's PTE, V R W: 0x2048d007 (program 11)
```

`0x80007cf0` is program 02's `__stack_top`. Each program is its own ELF,
so for program 08 take its own, from
`"$BIN/llvm-nm" $E/08_where_free_memory_starts | grep __stack_top`, and the
first line then prints what 08's `clear the low 12 bits` row says.

**8. The broken files: compiled, never run.**

```sh
./show-errors.sh e0606

```

## Talking points that land

- **Something ran before your first instruction.** Six instructions in a ROM
  at `0x1000` set `a0` to the hart ID and `a1` to the device tree, then jump
  to `0x8000_0000`. Program 04 finds their values still in `a0`–`a2` when
  `main` starts. Nothing in the program wrote them.
- **`end` is an address, not a variable.** The linker defines it; Rust only
  declares it. Its address is the whole point, and it is not known until
  link time, which is why it cannot be a `const` and why reading it takes
  `unsafe` or `addr_of!`.
- **The stack grows down, and nothing stops it.** `sp` starts at the top of
  16 KiB. Program 03 recurses past the bottom and finds its own return
  address in `.bss`, with no fault and no message. A stub that pointed `sp` at
  the low end would do the same from its first prologue.
- **A free page is its own bookkeeping.** Program 07 stores one address into
  the first 8 bytes of a free page. That is all the free list needs from each
  page, and it costs nothing once the page is handed out.
- **Round up, then clear.** Adding `0xFFF` and clearing the low 12 bits
  finds the first page that starts at or after an address. Clearing alone
  rounds down, into memory that is already in use.
- **A PTE is arithmetic.** `pa >> 12` drops the offset, `<< 10` makes room
  for the flags, and `| V R W` fills them in. Decode it the same way,
  backwards; decoding with `>> 12` gives an address that looks right and is
  not.

## Questions students ask, with short answers

**"Why does program 08 start free memory at `__stack_top` and not `end`?"**
Because this runtime put its stack right after the image. rv6's boot stack is
an array inside `.bss`, so in rv6 everything from `end` up is free.

**"Is `satp = 0` a bug?"** No. Nothing has written it yet, and MODE 0 is
Bare: no translation. Machine mode is never translated anyway. rv6 turns
paging on in week 10.

**"How did program 13 change its own code?"** With paging off in machine
mode, RAM is readable, writable and executable, so one store rewrote an
instruction and `fence.i` made the CPU fetch it again. With a page table
that maps code R X, that store is a page fault: that is W xor X.

**"Can I print a float?"** Yes, now: the runtime turns the FPU on before
`main`. Without that, QEMU starts with the FPU off, and the first float
instruction hangs the machine.
