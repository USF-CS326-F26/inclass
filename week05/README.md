## Talking points that land

- **A descriptor is an index, and the kernel hands out the lowest free one.**
  `01` gets 3, 4 and 5, then 4 again after a close. A leak does not fail where
  the `close` was forgotten. It fails at a later `open` of a file that exists,
  which on rv6 is the fourteenth.
- **Only 0 means the end.** The terminal answers 6, then 3, and neither is the
  end; the file answers 512, 512, 76, and the 76 is not the end either.
  `buf[..n]` is the read's answer, and everything past `n` is left over from
  before (`02`).
- **A bigger buffer buys fewer traps, fast, and then hardly any.** 1 to 512
  bytes removes 1,046,528 calls. 512 bytes to 64 KiB removes 2,032 more, at 128
  times the memory. On rv6 the kernel's 128-byte cap sets the count whatever
  you declare (`03`).
- **A short write is a number you have to read.** Bare `write` in `04` loses
  10 of 30 bytes and still returns `Ok`. The host takes every write whole, so
  no test catches it. `write_all` costs nothing when the first write takes
  everything.
- **The status describes the whole run.** Set it on failure and never clear
  it (`05`). grep's 1 is an answer, not a failure, and that is what `&&`
  reads. A status is one byte, which is why nobody returns a count.
- **`len` counts bytes.** `"año".len()` is 4. Every byte of a multi-byte
  character is `0x80` or above, so a byte search for `\n` never lands inside
  one, and the commands never need to decode (`06`).
- **Where the state lives decides whether chunking matters.** Same loop,
  `after_cr` in the caller or in the callee. `07` tries every split point, and
  the forgetful version is wrong exactly where a read ends between `\r` and
  `\n`. The kernel chooses where reads end. (A routine that acts when
  something *ends* also needs a flush after the last read: that is Problem 3,
  and nothing here works it.)
- **A line is a slice of your buffer, on loan.** `08` prints the page's
  compaction rows. E0502, E0506 and E0499 are the three ways to touch the
  buffer while the loan is out, and C compiles all three.
- **Count both fenceposts.** A `k`-byte needle on an `n`-byte line has starts
  0 through `n - k`, and `0..n - k` skips the last one. Decide the empty needle
  and the too-long needle before subtracting anything (`10`).
- **Judge `head` by what it does not read.** `11` reads 1,024 of 10,000,000,000
  bytes for one line. `yes` is a source whose `read` never says 0 at all, so
  only a program that stops can finish.

## Questions students ask, with short answers

**"Why does the next `open` get 4 and not 6?"** POSIX requires the lowest
descriptor not in use, and xv6's `fdalloc` scans its table from 0 the same way.
A shell's `>` depends on it: close 1, open the file, and the file lands on 1.

**"Why doesn't `read` just wait until the buffer is full?"** Because more may
never come, or not soon. An interactive `cat` would echo nothing until you had
typed 512 keys. Returning what is ready lets the program act on it now.

**"There is a `write_all`. Why is there no `read_all`?"** std has one,
`read_exact`, and a filter does not want it: on a terminal it waits for bytes
nobody has typed yet. A filter handles what arrived and asks again.

**"Does the buffer size ever change the output?"** It should not. It changes
how many calls happen. If the output changes with the chunking, the code
ignored `n` (`02`) or reset some state between reads (`07`).

**"std's `BufRead::lines()` works in a `for` loop. Why not `Lines`?"** std's
hands you a new `String` for every line, which is a heap allocation each time.
ulib's hands you a slice of your own buffer, which is free and dies at the
next call. `Iterator` cannot express "dies at the next call", so `Lines` gets
`while let` instead (E0277).

**"The byte is ASCII. Why won't `b == '\t'` compile?"** A `char` is a Unicode
scalar value and a `u8` is a byte, and Rust will not pick an encoding for you.
`b'\t'` states it at the literal (E0308).

**"Is an empty needle really a match?"** Yes. It has no byte that could
mismatch. std agrees, `"heart".contains("")` is `true`, and `grep ''` prints
every line.

**"My release build printed a huge number instead of panicking."** A release
build wraps `2 - 5` to a number near 2^64. The first index that uses it fails
the bounds check, so the program stops anyway, and on rv6 the stop prints one
word. `checked_sub` says `None` in both builds.
