## Running it

```bash
cd examples
cargo run --bin 01_registers      # ... through 13_the_panic_handler
```

`cargo run` builds for `riscv64gc-unknown-none-elf` and hands the ELF to
`qemu-system-riscv64`, exactly as `oslings run 20a_asm_bridge` does. The
program prints over the UART and powers QEMU off when it is done. If one ever
hangs, <kbd>Ctrl</kbd>-<kbd>A</kbd> then <kbd>x</kbd> quits QEMU. You need
the two things `oslings doctor` already checks: `rustup target add
riscv64gc-unknown-none-elf` and QEMU.

```bash
cd examples && ./show-errors.sh
```

`show-errors.sh` walks all seven compile failures, pausing between each; pass a
substring to jump to one: `./show-errors.sh e0133`. They compile for the same
bare-metal target, and nothing under `broken/` is part of the package.
`10_unsafe_does_not_turn_off` builds with one warning on purpose, and
`13_the_panic_handler` ends in a panic on purpose, with exit status 1.

Open `examples.html` to see every program beside the output it printed. Unlike
weeks 2 to 4 it has no **Edit and run**: a browser, or the Rust Playground,
cannot boot a RISC-V machine. The output on the page was captured under QEMU
on the instructor's machine, and the footer says which versions. Click an
output line to light up the `println!` that printed it, `Space` steps through
the sections, and clicking a section's number copies a link to it. After
changing a program, rebuild the page from the repo root with `python3
tools/pointat.py week06`, which needs QEMU; see "Cross-target weeks" in
`tools/README.md`.

## The runtime every program shares

`src/lib.rs` is not on the page. It is the part every program would
otherwise repeat, and each program opts in with three lines:

```rust
week06::entry!(main);                               // boot, run main, power off

#[panic_handler]
fn panic(info: &core::panic::PanicInfo) -> ! {      // 30k: every no_std program has one
    week06::report_panic(info)
}
```

- `entry!(main)` emits `_entry`, the first instruction QEMU runs: it points
  `sp` at the stack `link.ld` reserves and jumps to `__week06_start`, which
  calls `main` and then powers off. Program 12 prints every one of those
  addresses.
- `println!` and `print!` are `core::fmt` writing bytes to the UART's
  transmit register at `0x1000_0000`. With no heap, formatting still works
  (program 11).
- `exit(code)` stores to the SiFive test finisher at `0x10_0000`, which ends
  QEMU with that status. `report_panic` prints the panic and exits with 1.

rv6 has its own version of each piece; none of these is course code you
will be asked to write.

## The seven failures

| File | Error | Fix shown in the header comment |
|---|---|---|
| `e0463_forgot_no_std.rs` | the target has no `std` to link | `#![no_std]`, with the `!` |
| `e0601_forgot_no_main.rs` | rustc wants a `main` nobody will call | `#![no_main]`, not an empty `fn main` |
| `panic_handler_required.rs` | a `no_std` program with nowhere for a panic to go | one `#[panic_handler]` returning `!` |
| `e0152_two_panic_handlers.rs` | "exactly one" holds across the whole program | delete one |
| `e0133_raw_deref_needs_unsafe.rs` | reading through a raw pointer outside `unsafe` | `unsafe { read_volatile(MTIME) }`, or an `unsafe fn` |
| `e0308_unsafe_keeps_types.rs` | a `u64` register read into a `u32` | take the register's type, or say `as u32` |
| `e0433_vec_needs_alloc.rs` | `Vec` is in `alloc`, not `core` | a fixed array and a count, until there is a heap |

with `--emit=metadata`. The panic-handler error has no code at all.

## Talking points that land

- **Assembly is not magic; it is the calling convention.** `find_byte` works
  because both sides agree that the pointer is in `a0` and the byte in `a1`.
  Nothing checks the agreement. The `extern "C"` line is the only place it is
  written down, which is why every call is `unsafe`.
- **`ret` has no memory.** It jumps to whatever `ra` holds at that instant.
  Program 01 shows `ra` pointing into `main`; program 07 loads a different
  `ra` and a different `sp`, and the same `ret` resumes a function nobody
  called. That is a context switch with half the work missing, and `35k` is
  the other half.
- **Saving `s1` is only visible to a caller that uses it.** `rude` returns
  the right answer. Its only victim is `keeper`, which finds `0x63` where it
  left `0x5151`. A unit test of `rude` alone passes; that is why the rule is a
  convention you follow, not a bug you find.
- **The compiler assumes memory is memory.** Two plain stores to the same
  address are one store, and a load in a loop with no stores is one load. For
  the UART that means a lost byte; for the clock, a loop that never sees time
  pass. `volatile` says "this access is the point".
- **`unsafe` is a promise you write down once.** `end_of` takes a `&Span`, and
  a reference is already proof of everything `span_end` needs. So the
  `unsafe` block lives in one line inside it, and every caller is safe code.
- **`no_std` is a smaller Rust, not a different one.** Iterators, `Option`,
  `?`, slices and `core::fmt` all work in program 11 with no heap and no OS.
  What is gone is anything that needs a service: files, threads, and the
  allocator behind `Vec`.

## Questions students ask, with short answers

**"Why is there no Edit and run on this page?"** The Playground runs Linux
binaries for the machine it runs on. These programs need a RISC-V CPU, a UART
at `0x1000_0000` and a test finisher at `0x10_0000`, which only QEMU's `virt`
board provides. Run them yourself with `cargo run --bin …`; it takes a second.

**"Where does `println!` come from without `std`?"** From `src/lib.rs`: a
twenty-line macro that formats with `core::fmt` and stores each byte to the
UART. `std`'s `println!` does the same, then goes through a `write` system call
to reach the terminal. Here there is no system to call.

**"Why opt-level 1?"** Without optimization the compiler performs every load and
store you wrote, and program 09's plain versions happen to work. A kernel is
built optimized, and that is when the missing `volatile` bites. Programs
01–08 and 10–13 read the same either way.

**"Why does program 13 exit with 1?"** Its panic handler powers QEMU off with a
failure status, the way rv6's prints `OSLINGS:FAIL (panic)` and stops. The
`//! Exit: 1` line in its header tells `tools/pointat.py --check` that 1 is
the expected status.
